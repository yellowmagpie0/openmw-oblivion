## Player experience

- Display the authored quest title and the current available journal entry. Keep the HUD compact with the title and destination label, and show the longer entry in the map panel where it can be read in full. Use reference, base-object and cell names for destination labels and localized UI strings for generic actions and empty states.
- Reuse the existing map binding. Add **Show objective** to center the pin on the relevant map, and a compact list of current quests with an **Automatic** option and a manual tracking choice. Expose both actions through existing gamepad focus and mouse input. Use a distinctive pin shape and label alongside color, and keep the objective readable with the minimap hidden.
- When an authored target is indoors or in another worldspace, use a verified connection to show the entrance or next transition. In the target's cell, use its current position. When a quest provides text but no eligible target, show the text and leave the bearing empty. Where the destination is known and the route is uncertain, label the destination and omit the suggested next doorway. Bearings communicate direction. The map and any existing road information support route choice.

## Content boundary

Production code and shipped tracker configuration use record types, winning records, runtime state and engine navigation services. Quest names, FormIDs, places and expected progressions in this plan belong in test fixtures and acceptance evidence. Quest-specific tables, hand-written regional pins, stage ranges, instructions and priority overrides are out of scope, including in shipped manifests. The same tracker should accept a mod-added quest or winning override through the normal load order.

`QSTA` identifies a destination and its eligibility. It does not always identify an outdoor approach, a prerequisite quest, or the intended route past a scripted barrier. Derive an entrance from usable world connections where there is evidence. Use a different quest when the general tracker selects it after a player-facing update or the player selects it. Where shipped content gives only a journal entry or a destination behind an unqueryable barrier, show the available information. A general tracker cannot safely infer arbitrary script intent.

## Implementation sequence

### 1. Pin down progression and deliver the first travel marker

1. Build editable evidence-only scenarios for the original route, an unrelated official quest and a synthetic plugin or override. Record the winning quest targets, condition groups, script and INFO references and door pairs by canonical `FormKey`. Audit the original game's active-quest selection, active-quest changes after completed conversations, stage-entry flags, and the timing of conditional journal entries before claiming native equivalence.
2. In the TES4 `QUST` loader, retain ordered `QSTA` entries with resolved reference keys, flags and scoped `CTDA`/`CTDT` lists. Retain `CNAM` text and `QSDT` flags and conditions in their respective stage entries. Preserve quest-level dialogue conditions and stage-result identities and execution behavior. Validate lengths, stable form remapping, and ordered duplicates. Update the skipped-subrecord census. A compact current-entry view is sufficient for this deliverable.
3. Resolve target conditions against a read-only quest/world snapshot through the existing native condition evaluator. Implement condition functions by their game semantics, exercising stage, completed-stage, cell and reference/global queries as the cases require. Preserve authored order and OR groups and present multiple simultaneously eligible targets when the data provides them. Treat an unsupported or unknown result as unresolved, report it in a deduplicated diagnostic and retain any independently valid targets. Keep current stage distinct from completed-stage membership.
4. Have the quest runtime record the current eligible player-facing entry when the relevant stage result is processed. Audit event timing and repeat/completion semantics. Publish a coherent objective view once nested script effects settle. Reuse native stage and running state, and determine tracker eligibility from proven entry and completion semantics. Refresh target conditions as world state changes. Keep previously earned journal text keyed by stage and entry ordinal so later condition changes cannot rewrite that history. For old saves, recover targets from current state and show only text that is safely recoverable, falling back to the quest title when historical branch selection is ambiguous.
5. Use the same tracking policy for all quests. If the native active-quest rules can be established, use them. Otherwise make the fallback explicit: a manual selection stays selected while valid, and Automatic follows the most recent eligible player-facing quest update. Housekeeping stages and target-only refreshes should not steal focus. Use authored priority and a stable key as deterministic fallbacks where older saves lack update order. Let the player choose an eligible quest if multiple are relevant, including text-only quests. If required, add backward-compatible optional save metadata for the manual selection, entry identity and update order. Pins, world positions and route calculations are derived after load.
6. Ship the first vertical slice once an earned sewer save and a cold reload show the Weynon destination and an unrelated quest works through the same tracker. The pin is independent of discovery and fast travel. If the ordinary route needs a currently deferred command such as `ShowMap`, implement the command at its existing gameplay boundary and verify its semantics there.

Implementation entry points are the TES4 quest loader, the native condition evaluator, the existing quest state and the shared map. ### 2. Resolve doors and moving actors, then join the Weynon–Kvatch route

1. Let the world layer produce both a regional destination and the immediate actionable target for the player’s cell. Within the same cell or exterior worldspace, use current reference coordinates. For a loaded actor, prefer its live position. For an unloaded actor, consult the existing saved and low-process positions before using the winning authored location. Respect enabled state, enable parents, deletion, and death when the action requires a living actor. Query by placed reference identity and avoid materializing distant cells, starting scripts, or storing GUI-facing pointers across cell changes.
2. Build or reuse a read-only index of directed transitions from winning `XTEL` links and world/cell identities. Consume dynamic destinations only when the owning gameplay service exposes them, including gates if their destination is assigned at runtime. Start with generic door links and inspect the existing interior-to-exterior projection for concepts to reuse. Search from the player or target through eligible transitions and distinguish the destination's exterior projection from the first transition to take now. Keep interior coordinates local. Account for disabled references, known locks and one-way connections, and handle cycles and multiple exits deterministically. A worldspace transition graph cannot guarantee walkability within terrain or infer an arbitrary script's lockout. Suppress a claimed next step where a connection is unknown or blocked. Cache topology by content revision and recheck dynamic availability as needed without loading distant cells or rebuilding widgets every frame.
3. Render both cues from the same objective view. Reuse world-map projection, local-map transforms, zoom and pan. Identify or clamp off-map objectives clearly, with a directional cue for offscreen targets and no stale bearing if the player is on the target or in the wrong world. Update on settled quest transitions, load, cell change, and changed target position or availability. Follow existing HUD visibility and dialogue behavior. Bind the map action to the accepted gamepad focus model and preserve the map’s normal player-centering action.
4. Walk out of the sewers, cross to Weynon, use the correct door, speak to Jauffre, verify delivery, and continue by road to the Kvatch camp and Savlian. Fix gameplay dependencies only when a reproduced failure blocks this course. Fix them at their existing ownership boundary, such as original INFO conditions/results, inventory transfer, quest events, or a real door transition. Keep guidance read-only throughout.

### 3. Follow the siege through the Kvatch entrance

1. Add the MS48 entry step and actual gate transition to the joined course. Verify the cue changes on entry and that a reload inside the realm never points across unrelated world coordinates. If a game service owns a gate link absent from the static index, expose it by transition type for all affected content. Use eligible authored targets and earned journal text on deeper siege beats. Use the current Kvatch handoff to identify remaining gameplay prerequisites.
2. After ordinary gate closure and the post-gate conversation work end to end, verify the transition back to Savlian, the usable entrance into ruined Kvatch, the chapel, and the switch to Martin. Run the chapel blocked/unblocked variants and return-leg handoff. Record the first-gate delivery independently if the existing siege course still blocks the chapel run.
