M15: combat, stealth, crime, and jail

A gameplay programmer’s tour of what the local OpenMW Oblivion fork has built, what is being wired together now, and what still has to work in a real playthrough.

Repository snapshot: 5 October 2026 · branch master · based on committed history, the M15 handoff, and the current local diff

The state of the milestone

M15 is a long-running compatibility effort, not a finished combat feature. The native Oblivion data model and much of the rule math are reviewed and implemented. Native melee and projectile foundations exist. The current work is still closing gaps in restore safety and the physical bow/pickup pipeline. Stealth, crime, arrest, jail, official campaign playthroughs, and final acceptance remain ahead.

Important status distinction: the report marks S0, S1 and S2 passed; S3, S4 and S5 in progress; S6–S14 pending. “Passed” here means that stage’s declared data/rule or harness gate, not that Oblivion gameplay is complete. No full M15 normal-input campaign has been accepted.

Done: knowledge and pure rules

Native TES4 inputs are parsed and audited, and reviewed formulas have independent expected values and provenance.

In progress: world integration

Combat actions, actor state, inventory, scene objects, save data and callbacks are being joined without partial updates.

Still ahead: player-visible outcomes

AI fights, sneak and pickpocket, witnesses, guards, jail, and the official content routes still need end-to-end proof.

How the implementation is shaped

OpenMW is a shared engine with support for more than one game’s data and rules. This fork adds an Oblivion-native path alongside older Morrowind-shaped systems. The main risk is allowing a familiar shared helper to quietly apply the wrong game’s rule. M15 therefore separates three jobs: TES4 records supply inputs, pure native rules calculate outcomes, and world services apply those outcomes to live actors and objects.

Input, AI, or script requests an action
→
Native service validates actors and equipment
→
Contact, release, transfer, or arrest becomes authoritative
→
Rules update health, fatigue, item condition, crime, or jail state
→
Animation, UI, sound and scripts observe the committed result
→
The same state can be saved and restored

Think of this as one simulation authority with several adapters. Input and AI propose actions; they should not each implement their own damage or crime math. The shared animation/physics engine can provide motion and contacts, while TES4-specific services decide what those contacts mean. Inventory and item condition remain owned by the existing native inventory system rather than copied into a second combat-only inventory.

Stable form keys identify actors and items across load order and save/load. Persistent records store identities and logical state, not transient pointers or renderer handles. Typed data and fail-closed diagnostics make missing or malformed TES4 inputs visible instead of borrowing a Morrowind default.

What is already implemented

TES4 data and rule audit

S2 adds typed support for combat styles and the actor/faction inputs that feed native policy. The report describes a complete audit of 11 official plugins, a winning-record/hash/count lock, 130 explained policies covering 3,636 actors, and independent comparison of 7,540 fields. Pure rule comparisons include tens of thousands of original-instruction results. The mastery matrix covers 41 abilities. This gives later gameplay code a reviewed contract for rounding, thresholds, data defaults and exceptional records.

This is the equivalent of having a trustworthy design spec and tested math library. It does not mean an NPC can yet complete a fight or that a player can finish the Arena.

Native actor and runtime foundations

The fork already has native actor stats, inventory and actor identity work from earlier milestones. M15’s S3 work extends the runtime save schema and connects native state to world restore. Recent committed work prepares character data, complete inventories and native actor views before publication; a migration fix preserves the equipment choices that old saves historically reconstructed from content.

The current uncommitted diff extends that transaction to ObScript state. It builds the restored script instances and quest state privately, checks program identities, locals, duplicate instances and winning quest records, and only then swaps them into the live script manager. World restore now prepares this before publishing the broader replacement. The goal is that a bad script binding cannot leave the player’s inventory, clock or dynamic-reference identity half-restored. The local diff also adds focused world regression cases for cancel/move/commit, invalid bindings and omitted quest defaults. Those tests are present in the working tree; this review did not run them.

Melee and block foundations

S4 has a native attack/contact route for ordinary Player and NPC cases, block and item wear logic, cancellation paths, stock sound recordings, and persisted timed knockback work. Many recent commits show work around actual input/action publication and avoiding side effects before a valid contact. The report still calls out incomplete actor/power/mastery/reaction coverage and the full restart gate.

Bow, projectile and pickup foundations

S5 now has saved bow-input state, held-arrow geometry, shared swept projectile physics, and careful publication for equipment breakage and loose items. Recent checkpoints preserve exact item extras (condition, charge, usage and ownership), derive dropped-weapon placement from actual renderer bindings, retain loose-body definitions/poses, and stage rendering, physics, navigation, inventory and script notifications before a pickup becomes visible to observers.

The design is deliberately transactional because a pickup touches several engine subsystems. If the item disappears from the scene but inventory insertion fails, or inventory grants it before collision/navigation removal succeeds, the player can duplicate or lose it. The latest committed pickup checkpoint prepares these resources first, then commits the source debit and inventory registration before observer callbacks. Bow launch, native flight/impact/recovery and normal-input acceptance are still open.

Why so much effort goes into transactions

From the player’s view, “load save,” “take sword,” or “release arrow” is one action. Inside an engine, each may touch multiple owners: save data, inventory stacks, equipped-item views, world reference registries, scene graph, physics scheduler, navigation index, Lua events and UI observers. An exception or callback halfway through can expose contradictory state.

The implementation pattern is prepare → validate → commit → notify. Preparation allocates and resolves everything while the old world is still intact. Validation checks that the assumptions still hold. Commit swaps or removes the prepared state in a controlled, low-failure section. Callbacks run after publication, so observers see a complete result. Prepared handles can be discarded without changing the live world, and single-use commits prevent accidental replay.

This matters especially for saving mid-combat. An arrow must not hit twice after reload; an equipped weapon must not vanish during a drop; an observer must not see an item before it has a registered owner. The same rules apply to arrest and jail later, where confiscation, bounty, sentence and teleport need to form one coherent outcome.

What is left to prove

Implementation checkpoints and unit/world fixtures are useful, but the player-facing acceptance target is much higher. The staged plan requires real input and real content, with continuation in a fresh process. The remaining work broadly falls into these groups:

  • Finish S3: complete load/cache reconciliation, populated historical migrations beyond the current chunk, queued callbacks and passive-effect migration, and active-action save/restart continuation.
  • Finish S4–S5: cover the remaining attacker/target, power attack, mastery, reaction, control and projectile cases; connect bow input through launch, collision, damage, recovery and save/load; prove NPC equipment drops and normal pickup behavior.
  • Build S6–S8: physical death/corpse/loot and essential recovery; combat-capable native AI that resumes its schedule; sneak and pickpocket through normal interaction and the existing perception authority.
  • Build S9–S12: witnessed crime and legal exceptions, guard pursuit and arrest choices, confiscation/fines, jail time/property/release/escape, and the actual script/dialogue paths needed by those actions.
  • Run S13–S14: complete the selected official campaigns with ordinary gameplay, inspect the resulting media, continue saves in new processes, compare with the original game, and run the full required regression/sanitizer/performance matrix.
Acceptance language: a source change can be implemented; a record can be parsed; a rule can match the original executable; an engine fixture can pass; and the game can still fail in normal play. The report keeps those claims separate. Full M15 completion means the required player routes and persistence work end to end.
